1. Общая схема «to‑be»

**Многоузловая (геораспределённая) инфраструктура**
- Используем несколько дата‑центров или несколько зон доступности (Zonal/Regional) в рамках одного или нескольких облачных провайдеров (например, Yandex Cloud).
- Между ними на глобальном уровне работает DNS/GLSB, распределяя трафик пользователей по принципу «ближайшего» ЦОД (geoDNS) и/или по принципу «наименее загруженного».

**Kubernetes‑кластеры**
- В каждом регионе (или зоне доступности) развёртывается отдельный кластер Kubernetes.
  - *Почему не «растянутый» кластер?* Для отказоустойчивости и снижения сетевых задержек надёжнее иметь независимые кластеры, между которыми при необходимости происходит failover на уровне балансировки.
- Внутри каждого кластера:
  - Nginx Ingress или аналогичный компонент принимает трафик от глобального балансировщика;
  - App POD (микросервисы) масштабируются горизонтально с помощью Horizontal Pod Autoscaler (HPA), используя метрики (CPU, кол-во запросов и т.д.) из Prometheus.
  - В каждом кластере хранится только код приложений и кэшируемые данные; основная БД синхронизируется отдельно (см. ниже).

**Балансировка нагрузки (DNS/GLSB + Health‑checks)**
- DNS/GLSB (Global Load Balancer) контролирует доступность каждого кластера/ЦОД путём health‑check. Если один регион недоступен или перегружен, трафик перенаправляется в другой.
- На Ingress‑уровне внутри каждого кластера также настраиваются health‑checks, чтобы Kubernetes сам «выводил» из ротации неработающие поды.

**Унифицированное время отклика из разных регионов**
- За счёт глобального балансировщика и выделенных Kubernetes‑кластеров в разных локациях пользователи из разных регионов РФ будут подключаться к «ближайшему» ЦОД, что снижает сетевые задержки и выравнивает время загрузки страниц.

**База данных (PostgreSQL + Patroni + HAProxy)**
- Чтобы обеспечить RTO=45 мин и RPO=15 мин, в каждом регионе может быть как минимум по одному узлу PostgreSQL; при этом на одном из регионов (или в одной из зон) находится «primary», а в остальных — «replica».
- Patroni + внешний сервис консенсуса (например, etcd/Consul/ZooKeeper) обеспечивает автоматическую смену роли (failover) при сбоях, а HAProxy даёт единый «endpoint» для приложений.
- Streaming Replication между узлами PostgreSQL в разных кластерах гарантирует синхронизацию данных. С учётом RPO=15 мин можно настроить либо более агрессивную асинхронную репликацию (с минимальным отставанием), либо частично‑синхронную репликацию. Выбор зависит от уровня допустимых задержек записи и требований к Consistency.
- Для резервного копирования (backup) используется либо встроенный механизм (basebackup, barman и т.д.), либо управляемый сервис от облачного провайдера. Хранение бэкапов — в объектном хранилище, доступном из всех регионов.

**Шардирование БД**
- При общем объёме данных в ~50 GB и ограниченном наборе сущностей (клиенты, продукты, заявки) необходимости в шардировании пока нет. PostgreSQL + Patroni с репликами по регионам без проблем справится с такой нагрузкой.
- Однако при дальнейшем росте данных и трафика возможно внедрение логического шардирования (например, по регионам или сегментам клиентов) — при этом Patroni по‑прежнему может управлять кластерами, а каждое «шардированное» объединение узлов будет иметь свой слой управления.

2. Стратегия масштабирования и отказоустойчивости

**Горизонтальное масштабирование (основное)**
- Увеличение числа подов приложения в Kubernetes (HPA). Позволяет «расти» вширь по мере увеличения запросов.
- При серьёзном росте данных в БД — добавление новых узлов БД (реплик) и при необходимости логическое разделение (шардирование).

**Вертикальное масштабирование**
- Увеличение объёмов памяти/CPU у уже существующих узлов БД или подов (в рамках лимитов облака). Используется как дополняющая стратегия, если увеличение количества узлов не даёт нужного прироста.

**Дополнительные зоны безопасности**
- Для соблюдения RTO/RPO при катастрофических сбоях (например, полная недоступность одного региона) важно иметь не менее двух изолированных зон/регионов.
- Данные реплицируются между ними, и при отказе одного региона глобальный балансировщик (DNS/GLSB) перенаправляет пользователей на оставшийся регион.

---

3. Конфигурация Kubernetes
- Независимые кластеры в каждой зоне/регионе, чтобы сбой или обновление в одном не затрагивали другие.
- Для единообразия конфигураций можно использовать тот же Helm‑чарт/Operators — CICD конвейер будет разворачивать одинаковую версию приложения в каждом регионе.
- (Комментарий на схеме: «Используются независимые кластеры Kubernetes для упрощения failover и снижения сетевой задержки между зонами»)

---

4. Балансировка нагрузки и Health Checks
- DNS/GLSB (geoDNS) проверяет доступность каждого кластера и направляет пользователей в «ближайший» или «здоровый» регион.
- На уровне Ingress контроллеров в Kubernetes используется дополнительный health‑check, чтобы исключать неподходящие поды из балансировки (app POD, Nginx и т.д.).
- (На схеме это указывается стрелками health‑check от балансировщика к каждому кластеру.)

---

5. Фейловер‑стратегия
- При сбое кластера/региона глобальный DNS/GLSB автоматически исключает его из ротации.
- Patroni на уровне БД обеспечивает переключение роли (primary → replica) внутри или между регионами. Технически это занимает секунды/минуты. При учёте организационных процедур (уведомления и т.п.), RTO=45 мин обычно достигается с запасом.
- RPO=15 мин достигается за счёт постоянной репликации и регулярного бэкапирования. Отставание реплики может быть < 1 мин, но формально бизнес позволяет до 15 мин потенциальной потери данных.
- (На схеме можно добавить «Failover → New Primary» стрелку и комментарий, что Patroni решает, кто становится лидером.)

---

6. Конфигурация базы данных
- PostgreSQL + Patroni + HAProxy:
  - Основной набор узлов (1 primary + N replicas) в одном регионе, плюс по 1—2 replica в других.
  - Постоянный streaming replication.
  - Автоматизированные бэкапы в распределённое хранилище (object storage).
- Шардирование пока не применяется (50 GB не критичны), но архитектура позволяет добавить его в будущем.

---

**Итоги**
- 99,9% доступности достигается за счёт независимых Kubernetes‑кластеров в разных регионах, глобальной балансировки (DNS/GLSB), отказоустойчивости на уровне базы (Patroni) и автоматического масштабирования (HPA).
- RTO=45 мин и RPO=15 мин обеспечиваются быстрой автоматикой фейловера на уровне БД, дублированием узлов в разных локациях и регулярными бэкапами.
- Единое время отклика: пользователи из разных часовых поясов РФ обслуживаются из ближайшего ЦОД, что минимизирует задержки и обеспечивает равномерную скорость работы приложения.
- Масштабирование «вширь» (горизонтальное) покрывает рост нагрузки и количества пользователей. При необходимости возможно дополнительное вертикальное масштабирование ключевых узлов.
- Таким образом, данная «to‑be» архитектура сочетает в себе геораспределённый уровень балансировки, независимые (и значит более устойчивые) кластеры Kubernetes и отказоустойчивую СУБД с репликами (Patroni+PostgreSQL), отвечая всем заявленным бизнес‑требованиям.

## Почему выбран подход Active‑Active

1. **Равномерное распределение нагрузки и снижение задержек**
   - При «Active‑Passive» трафик со всех регионов обрабатывался бы одной (активной) площадкой, а резервная фактически бездействовала бы до сбоя. Это увеличивает сетевые задержки для отдалённых пользователей и перегружает единый активный кластер.
   - «Active‑Active» позволяет каждому региону (или зоне доступности) обслуживать локальных пользователей напрямую, сокращая время отклика и распределяя нагрузку.

2. **Увеличенная пропускная способность**
   - Все площадки работают одновременно и обслуживают клиентов. Благодаря этому суммарная пропускная способность системы выше, чем при «Active‑Passive», и сервис может выдерживать резкие всплески трафика в том или ином регионе без деградации.

3. **Лучшее соответствие требованиям 24/7**
   - При высоком показателе доступности (99,9%) и жёстком RTO/RPO (45 мин / 15 мин) важно, чтобы сервис не зависел от одной площадки. В режиме «Active‑Active» каждая площадка уже «в строю» и при сбое одной из них пользователи бесшовно переключаются на другую без сложных дополнительных действий.

4. **Упрощённая масштабируемость**
   - Горизонтальное масштабирование становится проще: вы можете добавлять новые площадки (или расширять текущие) без простоя. Каждая новая площадка может сразу принимать часть трафика.

### Возможность переключаться на ближайший геокластер в случае сбоя

- **DNS/GLSB** (Global Load Balancer) или гео‑ориентированный DNS (geoDNS) в реальном времени выполняет health‑check всех «активных» площадок (регионов).
- Если какой‑то регион становится недоступным (по результатам health‑check), DNS/GLSB оперативно исключает его из ротации и направляет трафик на оставшиеся **активные** регионы.
- Пользователи из недоступного региона перенаправляются автоматически — с их стороны это выглядит как кратковременная задержка или переподключение, после чего приложение продолжает работать из другого дата‑центра.
- Одновременно, **Patroni** на уровне базы данных обеспечивает синхронизацию (репликацию) и, при необходимости, переключение роли «primary» (если требуются операции записи). При «Active‑Active» конфигурации с PostgreSQL обычно настроен «один active writer + несколько реплик» в разных регионах, однако при сбое primary в одном регионе Patroni автоматически «поднимает» другую реплику в другом регионе.
