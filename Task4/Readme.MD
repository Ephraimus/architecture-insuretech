# Задание 4. Проектирование продажи ОСАГО (Обновлённая версия, Kafka)

#### 1. Новый сервис `osago-aggregator`

1. Получает события «Новая заявка ОСАГО» из Kafka (топик `osago.requests`).
2. Отправляет заявки в страховые компании и опрашивает их API, сохраняя данные (ID заявки, статус, расчётную премию) в
   `osago-aggregator-db`.
3. Публикует частичные ответы по мере готовности в топик `osago.offers`.

#### 2. Зачем нужна база данных в `osago-aggregator`

1. **Устойчивость при сбоях**: если контейнер или процесс перезапускается, без базы вся информация о незавершённых
   заявках теряется. С базой после рестарта можно продолжить обработку с того же места.
2. **Обработка тайм-аутов (60 с)**: нужно надёжно хранить время старта запроса, чтобы корректно завершать опрос каждой
   СК. Без базы при рестартах эти данные исчезают.
3. **Горизонтальное масштабирование**: несколько экземпляров `osago-aggregator` должны иметь общее состояние и забирать
   заявки друг у друга, а не вести несогласованную локальную обработку.
4. **Реализация повторных запросов (Polling, Retry)**: иногда нужно периодически опрашивать API (при «длинном»
   ожидании). Без постоянного хранилища при сбое «этап» запроса снова потеряется.
5. **Логирование и аудит**: при необходимости проследить, когда и как обращались к СК, какие ответы и в какое время
   получали, требуется постоянное (пусть и краткосрочное) сохранение статусов.
6. **Гибкость при новых требованиях**: если понадобится хранить расширенные данные (детали запросов, дополнительные
   метаданные и т.п.), наличие базы упрощает доработки.

#### 3. Интеграция `core-app` и `osago-aggregator` (Event-Driven)

1. **`core-app` → `osago-aggregator`**
    - При создании новой заявки `core-app` публикует событие в Kafka (топик `osago.requests`), содержащее идентификатор
      заявки и её детали.
2. **`osago-aggregator`**
    - Подписан на `osago.requests`, обрабатывает новую заявку, сохраняет её в `osago-aggregator-db`, вызывает API
      страховых компаний, собирает ответы.
    - Публикует результаты в топик `osago.offers`.
3. **`core-app` ← `osago-aggregator`**
    - Слушает топик `osago.offers`, получает частичные предложения (ID заявки, условия, стоимость).
    - Обновляет статус у себя (в `core-db`), чтобы фронтенд мог отобразить результаты.

#### 4. API для веб-приложения (через `core-app`)

1. `POST /osago/apply` — отправка данных авто/клиента, возвращается ID заявки.
2. `GET /osago/apply/{reqId}/offers` — получение текущих ответов от СК.
3. Возможна реализация SSE/WebSocket для мгновенных уведомлений.

#### 5. Паттерны отказоустойчивости

1. **Circuit Breaker**: ограничивает неудачные вызовы к страховым компаниям.
2. **Rate Limiting**: защищает внешние API от перегрузки при пиковом числе заявок.
3. **Retry**: повторяет временно неудавшиеся запросы.
4. **Timeout (60 c)**: завершает ожидание на каждую СК, если нет ответа в отведённое время.

#### 6. Масштабирование

- **`core-app`** и **`osago-aggregator`** работают в нескольких экземплярах, подписывающихся на Kafka в своих Consumer
  Groups.
- **`osago-aggregator-db`** гарантирует сохранение состояния при переключениях и сбоях.
- Circuit Breaker и Rate Limiting учитывают совокупную нагрузку на каждую страховую компанию.
